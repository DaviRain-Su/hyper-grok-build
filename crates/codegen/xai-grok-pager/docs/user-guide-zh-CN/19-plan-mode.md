# 计划模式（Plan Mode）

计划模式是一个结构化的规划阶段：智能体先探索代码库并设计实现方案，再开始写任何代码。适用于「正确做法」确实存在歧义的任务——在动手写代码前先征得你的意见，可避免大量返工。

---

## 计划模式做什么

计划模式激活后，智能体会：

1. 阅读并搜索代码库，理解现有模式与架构
2. 设计实现方案，并写入计划文件
3. 可使用 `ask_user_question` 澄清具体问题
4. 调用 `exit_plan_mode` 将计划提交给你审批

计划模式为只读，**计划文件除外**：对计划文件（会话目录中的 `plan.md`）的编辑会自动批准；对其它任何文件的编辑会被直接拒绝——工具调用失败，并附带简短提示，说明只有计划文件路径可编辑。该约束在所有权限模式下都生效，包括始终批准（always-approve）。将规划与实现分离，便于你在写任何代码之前审阅并修正方案。

---

## 如何进入计划模式

### 智能体主动进入

当智能体判断任务存在真正的歧义时，会进入计划模式。它会调用 `enter_plan_mode` 工具，在计划模式激活前需要你的批准。若你拒绝，智能体继续保持普通模式。

**适合进入计划模式的触发场景：**

- 「给应用加上用户认证」——确实有歧义（session 与 JWT、令牌存储、中间件结构等）
- 「重新设计数据流水线」——重大重构，选错路线会浪费大量精力
- 「给 API 加缓存」——多种合理方案（Redis、内存、基于文件等）
- 「加入实时更新」——架构决策（WebSockets、SSE、轮询等）

**不适合使用计划模式：**

- 「在用户资料页加一个删除按钮」——实现路径清晰
- 「修 README 里的拼写错误」——直截了当
- 「更新 API 中的错误处理」——直接开工，有具体问题时再问
- 「我们能做搜索功能吗？」——用户想马上开始，而不是做计划

### 用户主动进入

你可以通过两种方式自行进入计划模式：

- **`/plan`** —— 进入计划模式。你发送下一条提示时，计划模式才会真正激活。运行 `/plan <description>` 可一步完成：进入计划模式，并以该描述启动一轮对话。
- **Shift+Tab** —— 循环切换会话模式：普通 → 计划 → 始终批准 → 再回到普通。从普通模式按一次即可进入计划模式。

计划已存在后，可运行 **`/view-plan`**（别名 `/show-plan`、`/plan-view`）重新打开已保存的预览。

---

## 计划文件

计划会写入会话目录中的 `plan.md`（路径为 `~/.grok/sessions/<cwd>/<session-id>/plan.md`，其中 `<cwd>` 是编码后的目录名，不是字面路径）。

计划文件包含：

- **背景（Context）** 小节：说明为何要做此变更
- 推荐方案（不是罗列所有备选）
- 需要修改的关键文件路径
- 可复用的现有函数与工具，及其文件路径
- 验证小节：说明如何端到端测试这些变更

---

## 计划审批

智能体完成规划后，会调用 `exit_plan_mode` 工具。该工具从磁盘读取计划文件，TUI 打开可滚动的计划预览，底部带有操作栏。

若智能体退出时尚未写入计划（`plan.md` 为空或不存在），仍会打开同一审批界面，并显示清晰的空状态提示，便于你批准并开始实现、请求修改（让智能体回到规划），或退出。在 minimal 模式下，空状态提示会写入滚动历史，控件条标题显示为 **No plan written yet**。

### 审阅计划

用方向键或 `j`/`k` 滚动计划。操作栏支持以下快捷键：

| 快捷键 | 操作                                                                                               |
| -------- | ---------------------------------------------------------------------------------------------------- |
| `a`      | 批准计划并开始构建。若有待发送评论，显示为 `approve w/ comments`，会在批准时一并发送。 |
| `s`      | 请求修改。焦点移到提示输入区，可输入修订说明；按 `Enter` 发送。 |
| `c`      | 对选中的行或行范围添加评论。                                                          |
| `q`      | 退出计划——不批准并放弃计划，同时关闭计划模式。                              |

按 `Tab` 可在计划预览与提示输入区之间切换焦点。

### 提供反馈

审批视图有三种焦点状态：

- **预览（Preview）**：滚动计划并选择要评论的行。
- **评论（Commenting）**：对选中的行范围添加行内评论（按 `c`，或在某行上按 `Enter`）。
- **提示（Prompt）**：输入自由形式的修订说明。

按 `Tab` 在预览与提示输入区之间切换。发送反馈后——行内评论、自由说明，或两者兼有——智能体会收到并修订计划。计划模式保持激活，便于你反复迭代。

### 离开审批视图

按 `Esc` 可将焦点从提示输入区回到计划预览。若要在未批准、也未发送反馈的情况下关闭审批，按 `q` 退出计划。退出会放弃当前提案，并关闭计划模式。

## 计划模式生命周期

计划模式状态机有四个状态：

| 状态          | 说明                                                    |
| -------------- | -------------------------------------------------------------- |
| `Inactive`     | 正常运行模式。无计划模式约束。               |
| `Pending`      | 客户端已打开计划模式，但尚未发送任何提示。  |
| `Active`       | 计划模式已激活。计划文件编辑自动批准；其它文件编辑被拒绝。 |
| `ExitPending`  | 用户在一轮对话进行中关闭了计划模式。          |

状态转换：

```
Inactive    --> Active   (enter_plan_mode tool called and approved -- skips Pending)
Inactive    --> Pending  (you toggle plan mode on with /plan or Shift+Tab)
Pending     --> Active   (your first prompt activates plan mode)
Active      --> Inactive (exit_plan_mode approved, or you toggle plan mode off when idle)
Active      --> ExitPending (you toggle plan mode off while a turn is in-flight)
ExitPending --> Inactive (after the turn completes)
```

计划模式状态会持久化到磁盘，进程重启后仍保留。瞬时状态（`Pending`、`ExitPending`）在重启时会折叠为 `Inactive`，因为它们依赖进行中的交互。

## 计划模式中的编辑

计划模式处于激活状态时，对计划文件的编辑会自动批准、无需确认，智能体可自由迭代计划。对**任何其它文件的编辑会在执行前被拒绝**——智能体会收到简短消息，说明只有计划文件路径可编辑。

该约束与权限模式无关：

- **始终批准（yolo）在计划模式下仍处于待命状态。** 非编辑类工具（bash 命令、读取、MCP 工具）仍会自动运行，但文件编辑会被拦截，直到你批准退出计划模式。计划获批后，始终批准在实现阶段恢复生效。
- bash 命令不会被检查是否写入文件——计划模式拦截的是编辑工具，而不是 shell 重定向。
- 子智能体不受父会话计划模式编辑门禁约束。每个子智能体都有独立的计划模式跟踪器（初始为 `Inactive`），因此 `general-purpose`（或其它具备写入能力）的子智能体可在父会话仍处于计划模式时编辑文件——并继承父会话的权限模式（含始终批准）。`explore` 等只读类型仍受自身工具集限制。

状态标志在计划模式激活时显示 `plan`。若底层启用了始终批准，计划模式退出后其标志会重新出现。

---

## 计划模式与压缩（Compaction）

在激活的计划模式会话中运行 `/compact` 时，计划模式状态会保留。压缩后的上下文会包含「计划模式仍激活」的提醒，因此智能体在压缩后会继续做规划。

---

## 何时适合使用计划模式

**适合使用计划模式的情况：**

- 存在显著架构歧义的任务（多种合理方案）
- 需求不清，需要先探索再实现
- 高影响重构，选错路线会浪费大量精力

**可跳过计划模式的情况：**

- 实现路径清晰的任务
- 一旦理解 bug 后修复方式已很明显的缺陷修复
- 遵循现有约定的功能添加
- 直截了当的修改（重命名、格式化、补充测试）
- 调研与探索类任务（改用子智能体）
